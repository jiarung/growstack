## <a id="0904-dli"></a>2026-09-04 — DLI 兩種算法的差異，原因**判斷過兩次都錯**

**症狀** 光譜法日 DLI 長期低於 lux 法，比值 0.51–1.64 逐日擺動。

**原因（第三版，2026-09-07 定案）** **就是上一則的光路遮擋，沒有第二個原因。**
遮擋排除後比值反轉 —— 光譜法現在比 lux 法**高** 40%：

```
台北整日   lux_dli  spec_dli  ratio
09-02       4.00     2.92     0.728   ← 遮擋中
09-03       3.74     1.93     0.515   ← 最糟
09-04       3.62     3.60     0.995   ← 修復當天（11:20 動手）
09-05       3.69     5.09     1.379   ← 第一個完整修復日
09-06       3.51     4.96     1.412   ← 第二個，穩定
```

原始症狀是「光譜法低那麼多」。**它現在不低了，是高的。**

**兩個被推翻的推論，都留著當記錄：**

**第一版（面板說明原文）**：「比值游走本身就是 CAL 尚未定案的證據」。
**不成立** —— `CAL` 在該查詢裡是寫死的常數，`DLI = CAL × ∫S` 對它是純線性的，
錯的 CAL 只會造成固定倍率，數學上不可能造成逐日擺動。

**第二版（2026-09-04 我的判斷）**：「主因是 `lux/54` 在燈下是錯的常數，
純日光與純燈下差 **2.7 倍**，而 84% 的積分 lux 落在 `mixed` cell；光路衰減只是次因」。
**主次顛倒了。** 光路修好後重量同一件事：

| 光源 | 遮擋中（09-04） | 修復後（09-07） |
|---|---:|---:|
| daylight | 1.55 | 1.60 |
| mixed | 0.78 | 1.41 |
| lamp | 0.57 | 1.41 |
| **日光÷燈下的差距** | **2.7×** | **1.14×** |

真正的光譜差距只有 **1.14×**。那 2.7 倍裡絕大部分是壞掉的感測器。

**為什麼會判錯（這才是要記住的）** 遮擋是**角度性**的 —— 日光和燈從不同方向進來，
被擋掉的比例不一樣。所以一個純機構故障，在按光源拆開的表格裡**長得完全像光譜效應**，
而且方向、量級都很有說服力。我當時把兩個原因分開列了，卻沒想到次因會汙染主因的量測本身。

> **一個會隨光源方向而異的故障，可以偽裝成任何「與光譜有關」的結論。**
> 排除幾何因素之前，不要對光譜下結論。

**仍然成立的部分**：`lux/54` 的 54 lm/µmol 確實是為太陽光定的，套在 LED 上沒有物理依據 ——
這是方法本身的性質，沒有改變。改變的是它的**實測影響量級**：1.14× 而不是 2.7×。

**處置** ✅ 症狀已解決。但**絕對尺度仍不可信**：`CAL` 尚未重配，而重配的前提
（通量比回到 6.0 以上）還沒滿足 —— 現行 5.19。見上一則。

## <a id="0907-lux-low"></a>2026-09-07 — lux 法遠低於光譜法：是預期物理，不是故障

**症狀** 光路修好後比值反轉並穩定：lux 法比光譜法低約 **1.41×**（09-05 1.379、09-06 1.412）。
與 [2026-09-04 的 DLI 那則](#0904-dli) 是同一件事的後續 —— 那則問「為什麼光譜法低」，
這則問「為什麼現在反過來」。

**證據 —— 燈的實測光譜（2026-09-05 19:00–20:00，純燈下，counts ÷ R）**

```
f415 14.0%   f445 28.3%   f480  7.1%    → 藍 415-480  49.4%
f515  9.1%   f555  9.1%                 → 綠 515-555  18.2%   ← 凹陷
f590 12.1%   f630 10.2%   f680 10.0%    → 紅 590-680  32.3%
```

藍＋紅雙峰、綠光凹陷 —— 標準園藝 LED。

**原因** `lux` 是明視覺加權，峰值 555 nm 綠光；這顆燈刻意避開綠光（對光合貢獻低、對人眼卻最亮）。
所以**同樣的光子數，它產生的流明比太陽少**，而 `lux/54` 的 54 lm/µmol 是為太陽光定的。

從八個通道的光譜形狀直接推算，不經過 `CAL`：

```
燈       明視覺加權 ÷ 光子加權 = 549.7
D65 日光 同一指標              = 672.2
→ 預測 lux/54 在燈下低估 1.22×
→ 實測 spec/lux 在 lamp cell    1.41×
```

**同方向、同量級。** 一個從光譜形狀算出來的預測，對上一個直接量到的比值。

**剩下的 1.41/1.22 = 1.16（約 16%）拆不開**，三個已知來源都指向同一件事：
`CAL` 已失效（07-16 擬合，之後經歷 07-22 與 08-11）、感測器還差 20% 未歸位
（會讓 S 偏低，也就是讓 1.41 **偏小**）、以及 AS7341 只有 8 個窄帶、
`Σ(counts/R × λ)` 只是對真實光譜的粗略近似。分開需要 Photone 地面實測。

**處置** ✅ 症狀已解釋，**不需要修**。這是方法本身的性質：
`lux/54` 在 LED 下沒有物理依據，而燈佔了 99% 的積分光量。

順序不可反：**先把感測器角度調回通量比 6.3 以上，再用 Photone 重配 `CAL`。**
光路沒回到基準就重配，等於把光學損失直接烤進 `CAL`
（`broker/PPFD-CAL-ROUTINE-PLAN.md`）。

**衍生出的兩條通則已升級到上層文件**，不重複在此：
- 「故障若與你正在變動的量相關，它會長得像結論」→ `MAINTENANCE.md` 失效類型 6
- 「原始 counts 不是光譜」「daylight cell 是 54 lux 曙光」→ `QUERYING.md` traps 5、6

## <a id="0909-scale-zero"></a>2026-09-09 — 秤的零點在漂，`used%` 的訊噪比小於 1 ♻

**症狀** OLED 上的耗竭% 看起來不對：多數盆停在 20–30%，而 `cactus-13-2` 顯示 **120%**
（超過定義上限）。使用者的原話是「損耗的顯示怪怪的」。

**證據** 相鄰秤重場次之間、同一批植物的重量變化中位數在 **−25.6 ~ +18.2 g** 之間來回跳，
而且符號交替。決定性的一筆：

```
08-25 11:14 → 08-25 20:32   同一天隔 9 小時   12 株全部變重，最少的也 +5.1 g
```

仙人掌不會在 9 小時內集體增重。四個相鄰場次出現這種情形（08-08→10、08-25 當日、
08-29→30、09-05→06）。空秤讀數（`quality=empty`，沒有盆在上面）本身也在
**−10.2 ~ +11.2 g** 之間漂，同一個量級。

**原因** 加性零點漂移，**與盆重無關**：

```
< 300 g 的盆 (n=33)   +10.5 g
> 800 g 的盆 (n=10)   +11.0 g
合併：增重 = +11.94 g − 0.0012 × 盆重     r = −0.08
```

279 g 的盆和 1221 g 的盆增一樣多。四倍的土不吸四倍的水，所以**不是質量**。
零點是在序列埠手動 tare 一次、存進 NVS，之後永不重取（`src/sensors.cpp:315-320`）。

**兩條被測試否定的假說**（都由使用者提出，都值得記下來）：

- **雨。** 四個異常場次有三個在雨天，看起來很像。但雨量單獨的 R² 只有 **0.02**，
  加進模型後係數 +0.069 g/mm、R² 完全不動（0.54 → 0.54）。雨天只是「冷且濕的日子」。
- **土/素燒盆吸空氣中的水。** 被上面的盆重測試否定 —— 那是真實質量，會隨土量縮放。

**未能分辨的**：溫度與濕度 `corr = −0.96`，統計上分不開（`dT` 單獨 R²=0.54，
`dH` 單獨 0.45）。所以「秤在量溫度」這個說法**不能宣稱** —— 只能說零點在漂。
（我一度這樣宣稱過，是過度解讀。）

**為什麼顯示會歪** 分子是兩個不同場次相減，帶 ±11–15 g 噪音；而典型分子只有約 10 g。
在 33–45 g 的 span 上，那是 ±34 個百分點的顯示噪音。**50% 以下基本上沒有內容；
85% 以上才是訊號。**

**處置** ♻ **零點漂移本身未修**，它每一次量測都會再來。
計畫與 Phase 0 查詢：[`scale-zero-drift-plan.md`](../scale-zero-drift-plan.md)。

排序在 `67e6b68` 之後改過一次，最便宜的一條換人了：
**恆定質量參考物**（砝碼或密封盒，自己有 tag，每場次掃一次）／
每場次先記一筆空秤讀數（只需改 Node-RED，不動韌體）／
溫度回歸修正（約消 54%，可回溯補歷史）／`sat_g` 改用次大值（只治標的一半）。

恆定質量勝過空秤讀數的理由是它**在負載下量**，對得上實際秤重的條件；空秤量的是
無負載的零點，而「漂移是否與負載有關」目前**並未驗證**（盆重測試只涵蓋 279–1221 g）。

**被否定的處置**：曾提議改韌體自動重取零點。使用者要求先有更強的證據，是對的 ——
加性偏移可以完全在伺服器端修掉，不需要動韌體。

## <a id="0911-invisible-watering"></a>2026-09-11 — 澆了水但沒再秤，那次澆水就不存在 ♻

**症狀** 使用者 09-10 傍晚澆了全部植株，隔天 `該澆水了嗎` 仍有兩株顯示
「距上次澆水 11.8 天」，其中 `cactus-13-2` 標成 **● 該澆水**（耗竭 137%）。


`cactus-12` 與 `cactus-13-2` 拿到了「澆水前」那一筆，**沒有拿到「澆水後」那一筆**。
`cactus-13-1` 也漏了同一輪，但它 09-11 15:23 被秤到，`+81.2 g` 當場補上。

**原因** 澆水是**推論**出來的，不是記錄下來的：`JUMP = 10.0`，相鄰兩次秤重之間
增加超過 10 g 才算一次澆水（`daily.json` 面板 10，與面板 2 的速率過濾、面板 11
的場次偵測同一個常數）。**沒有第二個讀數就沒有跳躍可看。**

系統沒有「澆水事件」這種東西可以記 —— 它只有重量。

**處置** ♻ **不是程式缺陷，是量測方法的邊界，而且每次跳過重秤都會再發生。**

重秤即可，錨點從 90 天歷史算，不需要當場補。`cactus-12` 於 09-11 15:47 重秤
2375.5 g（比 09-10 那筆高 62.5 g），耗竭當場從 84% 歸零。`cactus-13-2` 待重秤。

⚠ **但錨點會被記在「揭露它的那一筆」上**，不是實際澆水的時刻。`cactus-12` 因此
顯示 `days = 0.002`，而真正的澆水在 21.5 小時前 —— 少算約 0.9 天。這是方法本身
的性質，補一筆假讀數去修它會違反「raw 從未被改寫」（2026-09-08 已為此 revert 過
一次 backfill）。

**為什麼這不是可以忍的小事**：後果不是中性的。漏掉的那盆會慢慢爬到「該澆水」，
你照著面板澆，**就會澆第二次**。這個系統存在的理由正是要避免那件事。

## <a id="0912-ratio-corr"></a>2026-09-12 — 天花板是真的，但寫下來的理由是一個比值相關的假象 ✅

**症狀** `k-adoption-stuck` 對 `bh1750_lux_ref/daylight/diffuse` 連續告警 54 小時，
而告警的建議是「去補 Photone 量測」。該桶已經有 **13 個 session**（門檻 5），
卡的是精度：CI 相對寬度 **0.529**，門檻 0.20。補資料不會讓它過。

查為什麼過不了時，`photone-phase-d-migration.md` 的「已知天花板」給了答案 ——
`corr(k, 亮度) = +0.949`，感測器是壓縮響應，要換模型形狀。**那個答案是錯的。**

**證據**

```
實測（n=13）
  corr(k, photone) = +0.774     ← 原文那個數字最接近這個
  corr(k, sensor)  = +0.444
```

`k = photone / sensor`。**k 與 photone 共用分子**，所以兩者相關是建構出來的，
隨機資料也會給出高值 —— 比值相關的經典陷阱。對分母的 +0.444 才有意義，遠不到 0.949。

**而「換模型形狀」也被量測否定**。冪律 `ln(photone) = c + γ·ln(sensor)`：

```
去掉一筆離群 (n=12)          γ=1.227  R²=0.967  殘差 2.43×
再去掉最暗那點               γ=1.155  R²=0.874  殘差 2.47×
只留 sensor > 1000 (n=8)     γ=0.749  R²=0.189  殘差 2.36×   ← 8/12 樣本在這裡
```

R²=0.967 完全來自橫跨三個數量級；在樣本聚集處 R² 只有 0.19、γ 翻向反方向，
**而殘差在每一種切法下都是約 2.4× —— 冪律一克都沒消掉**。槓桿集中在一個比主群
低三個數量級的點上（對數 sensor 值：3.25，斷層，5.71–6.55，密集群 7.28–7.87）。

**原因** 散佈跟的是**時刻**，不是亮度：`corr(ln k, 時刻) = −0.665`。
`PPFD-CAL-ROUTINE-PLAN.md` 開頭早就寫過「欄杆陰影隨太陽移動，散佈 2.9×」——
我量到 2.4×，同一件事。**手機和感測器沒有在看同一束光**，而沒有任何模型形狀
能修好「兩個儀器在量不同的東西」。

同一顆感測器在燈下散佈只有 **3%**。但 `bh1750_lux_ref` **刻意被遮蔽於燈之外** ——
遮蔽就是它存在的理由，所以**它唯一能被量測的條件，正好是散佈最大的那個**。
這個天花板的性質是**選址**，不是建模。

**處置** ✅ 更正 `photone-phase-d-migration.md` 的天花板段落（天花板本身仍然成立，
換的是它的理由）。告警改為**每週一次**而非每 6 小時：加一條 `alertname` 子路由，
不動其他 7 條規則，也不加抑制名單 —— 那個桶仍然看得見，另外兩個真的需要量測的桶
繼續出現在同一封週報裡。即時通知由另一條規則 `k-model adoption needs a human`
（`for: 1m`）負責，沒有動它。

**留下的教訓**：`k = A / B` 這種量，**不要拿 k 去和 A 求相關** —— 那個相關是
建構出來的。要看 k 有沒有隨亮度變，看的是 **k 對 B**。這個陷阱讓一個真實的限制
掛上了一個錯誤的解釋，而那個解釋指向的是 blueprint 層級的改動。

## <a id="0901-nfc-scan"></a>2026-09-01 — 兩顆 tag 常常掃不到，有時得打開防水盒 ⚠

_量測方法已設計、尚未執行。原文寫在一份交接頁上，2026-09-16 搬進 repo 以免它只存在於一個網址。_

**症狀** `cactus-15b` 和 `cactus-10` 經常掃不到，有時要把防水盒打開、直接貼著才讀得到。
其他 tag 正常。

**證據** 使用者確認**那兩顆 tag 的背面不平，和盒壁之間有空隙**。空隙造成的失諧是
真實的物理原因，軟體只能買到餘裕，不能消除它。

**一個尚未驗證的懷疑** —— 兩個 timeout 疊在一起，外層可能把內層切斷：

```cpp
constexpr uint16_t TAG_POLL_MS = 50;        // measure.cpp:27  host 端每次讀取的 timeout
nfc.setPassiveActivationRetries(0x02);      // measure.cpp:231 PN532 內部重試 3 次
nfc.readPassiveTargetID(PN532_MIFARE_ISO14443A, uid, &len, TAG_POLL_MS);   // :59
```

PN532 被告知嘗試三次，但 host 在 50 ms 後就放棄。**若耦合微弱使每次嘗試變慢，
那個重試預算可能從來沒被用完** —— 那樣的話調高 `setPassiveActivationRetries` 完全
沒有效果，該動的是 `TAG_POLL_MS`。**先量再改。**

**量測補丁（未執行）** 只動 `src/measure.cpp` 一個檔案。它已經 include 了
`mqtt_client.h`，而 `mqttPublishDiagLine()` 正是為這種鑑識輸出宣告的 —— 不用註冊
diag 指令、不用改分派器。站台在陽台，用 MQTT 讀比接序列埠實際。

加在 `readTag()` 之前：

```cpp
// ---- NFC scan forensics — TEMPORARY, delete once 15b/10 are settled ----
// 失敗的 poll 是燒掉整個 TAG_POLL_MS，還是提早返回？擠在最上面那格代表 HOST
// 的 timeout 是綁定條件，該調的是 TAG_POLL_MS。提早返回代表耦合根本沒建立，
// 調長 timeout 買不到東西，要修的是 tag 背後那個空隙。
//
// 失敗只計數不印：readTag() 在 M_IDLE 每個 loop 都跑，每次印會把 log 淹掉。
// 成功則逐筆印 —— 它只在有人真的刷卡時發生，而它的耗時是答案的另一半。
constexpr uint32_t SCAN_REPORT_MS = 60000;
uint32_t scanFail[5] = {0};       // <10  <25  <40  <48  >=48 ms
uint32_t scanFailTotal = 0, scanOkN = 0, scanOkMaxMs = 0, scanReportedAt = 0;

static uint8_t scanBucket(uint32_t ms) {
    return ms < 10 ? 0 : ms < 25 ? 1 : ms < 40 ? 2 : ms < 48 ? 3 : 4;
}

// 每分鐘最多一行，而且只在數字有變動時才發 —— 閒置的站台保持安靜。
static void scanReport(uint32_t now) {
    static uint32_t lastTotal = 0;
    if (now - scanReportedAt < SCAN_REPORT_MS) return;
    scanReportedAt = now;
    uint32_t total = scanFailTotal + scanOkN;
    if (total == lastTotal) return;
    lastTotal = total;
    char line[128];
    snprintf(line, sizeof(line),
             "[nfc] fail <10:%u <25:%u <40:%u <48:%u >=48:%u | ok:%u maxOk:%ums",
             (unsigned)scanFail[0], (unsigned)scanFail[1], (unsigned)scanFail[2],
             (unsigned)scanFail[3], (unsigned)scanFail[4],
             (unsigned)scanOkN, (unsigned)scanOkMaxMs);
    logf("%s\n", line);
    mqttPublishDiagLine(line);    // 離線時是 no-op，序列埠仍有每一行
}
```

`readTag()`（`measure.cpp:55-62`）改成：

```cpp
bool readTag(char* out, size_t outsz) {
    uint8_t uid[7] = {0}, len = 0;
    uint32_t t0 = millis();
    bool ok = nfc.readPassiveTargetID(PN532_MIFARE_ISO14443A, uid, &len, TAG_POLL_MS);
    uint32_t dt = millis() - t0;
    if (!ok) { scanFail[scanBucket(dt)]++; scanFailTotal++; return false; }
    int n = 0;
    for (int i = 0; i < len && n < (int)outsz - 3; i++) n += snprintf(out + n, outsz - n, "%02X", uid[i]);
    scanOkN++; if (dt > scanOkMaxMs) scanOkMaxMs = dt;
    logf("[nfc] read %s in %ums\n", out, (unsigned)dt);
    return true;
}
```

`measureLoop()` 裡加一行 `scanReport(now);`（它第一行就有 `now`）。

**怎麼讀**

```sh
docker exec monitor-air-mqtt mosquitto_sub -t 'monitor-air/+/diag/out' -v
```

協定：先刷十次一定成功的 `cactus-01`，再刷十次 `15b`（盒子關著、平常的距離）。
逐次的 `[nfc] read … in Nms` 直接給對照。

| 直方圖的形狀 | 意思 | 該動什麼 |
|---|---|---|
| 失敗擠在 `>=48` | host 在 PN532 用完重試預算前就放棄 | `TAG_POLL_MS`，而且**只有它** |
| 失敗散在低桶 | 活化根本沒建立，不是時間不夠 | 軟體幫不上，修 tag 背後的空隙 |
| `maxOk` 接近 48 ms | 連成功都貼著上限，餘裕已經沒了 | 無論上面哪種都該調高 `TAG_POLL_MS` |
| 01 約 8 ms、15b 約 40 ms | 15b 是邊緣而非壞掉 | 適度調高 timeout 應能救回 |

**要respect的取捨** `readTag()` 在整個 timeout 期間**阻塞主迴圈**，而它在 M_IDLE
每個迭代都跑。調高 `TAG_POLL_MS` 會抬高最壞情況的迴圈延遲，而 OLED 的約 3 Hz
更新和 15 秒的遙測發布都疊在上面。比較好的做法是**只在秤上有負載時**用較長的
timeout —— 站台已經知道（`OLED_EMPTY_G = 30`）。

**處置** ⚠ **未執行。** 補丁是暫時的：五個檔案層級計數器加一行在熱路徑上的 log，
**在改常數的同一個 commit 裡刪掉**。它只為回答一個問題而存在。

## <a id="0917-ended-no-successor"></a>2026-09-17 — 派生式退役假設每一次結束都有後繼者 ✅

**症狀** `cactus-13-2` **果凍化**（組織腐爛成透明軟爛），植株已死。tag 從
`tag-map.json` 釋出之後，它仍然留在「該澆水了嗎」表上，**耗竭 168%、標著 ● 該澆水、
距上次澆水 17.6 天** —— 一個已經不存在的東西在要水。

**證據** 釋出 tag 之後，兩側的行為分岔：

```
Node-RED           容器內已無該 uid，且 flow 每次量測重讀 → 下次刷卡會是 plant_id="unknown"   ✓
publish-weight-ref note: 1 retired id(s) with history but no tag, no ref published   ✓
daily.json 面板 10  cactus-13-2  168.5%  days 17.6  ● 該澆水                          ✗
```

**原因** `MAINTENANCE.md` 的「Retired is derived, not declared」把退役定義成
**tag 歸屬**：誰擁有某個 uid 的**最近一次讀數**，誰就還存在。那個推導成立的前提是
**每一次結束都會把 tag 交給後繼者** —— 換盆是這樣（`cactus-03` → `cactus-03b`），
所以舊 id 立刻不再擁有任何 uid。

`live`。而面板讀的是 InfluxDB，**InfluxDB 不知道 `tag-map.json` 發生過什麼**，
這正是兩側分岔的地方：`publish-weight-ref.sh` 讀得到那個檔案，面板讀不到。

**處置** ✅ 面板 10/14 加一份 `ended` 名單（與 `controls` 並列但語意相反：控制組
**存在**且需要 retained ref，`ended` 的盆**不存在**）。13-2 移出後面板 10 從 25 列變 24 列。

`MAINTENANCE.md` 的該節已更正 —— 它花兩段論證「不要 retired 旗標」，而現在有一份了。
那個論證對它當初設想的情況仍然成立，只是那不是唯一的情況。新增「Ending a pot with
no successor」四步程序，第三步（加進 `ended`）就是這次漏掉會再犯的那一步。

**名單要保持短**：tag 一旦貼到別的盆上，推導就自己恢復運作，該條目就能拿掉。

**沒有刪除任何讀數。** 歷史是「這個盆存在過」的紀錄，`ended` 只是讓它不進決策表。

## <a id="0921-tagmap-mid-session"></a>2026-09-21 — 一邊掃一邊登錄，六盆新植株全部落成 `unknown` ✅

**現象** 新增的六盆掃完之後，面板和參考值裡一盆都沒有；`plant_weight` 多了六筆
`plant_id="unknown"`。

**原因兩個，疊在一起**

1. **時序**：`tag-map.json` 的存檔時間是 `00:04:56`，而掃描是 `00:03:24 → 00:05:28`
   —— 登錄動作發生在掃描**中間**。Node-RED 每次量測都重讀那個檔，所以前五筆掃過去時
   檔案裡還沒有它們。這不是 bug，是順序問題。
2. **真的漏了一個**：`53376417230001`（213.9 g）從頭到尾不在 `tag-map.json` 裡，
   對應的 `cactus-30` 連 reflect plant 都還沒建。掃了六盆，登錄了五盆。

從 uid 排序看得出缺口：`5335→cactus-25`、`5336→cactus-27`、`5338→cactus-28`，
中間的 `5337` 空著。掃描順序則完全對應編號（25/26/27/28/29），所以第六盆是 30。

**處置** ✅

- `add-plant.sh cactus-30` → `add-tag.sh 53376417230001 cactus-30`
- 六筆讀數用新的 `mark-weight.sh --set-plant` 從 `unknown` 搬到正確的 plant_id
- `publish-weight-ref.sh` → 六盆都取得 `first_anchor` 參考值，OLED 會顯示 `1st`

**`--set-plant` 的一個陷阱，寫在程式裡**

改 `plant_id` 和改 `quality` 不能共用同一個刪除述詞。`quality` 版本刪的是
`quality != 新值`；搬移時 quality 通常沒變，那個述詞會**什麼都匹配不到**，
於是同一筆讀數同時以兩個 plant_id 存在。所以搬移用自己的述詞（舊的 plant_id），
而且 `--plant` 變成**必填** —— 少了它，述詞會退化成「這個視窗裡的所有 plant_weight」，
把同場次其他盆全部刪掉。

**順手修掉兩個自己寫的 bug**（都只影響驗證訊息，資料始終正確）

- 驗證沿用 `quality` 的邏輯：搬移後舊 plant 的視窗是空的，於是把成功報成失敗。
- `awk '/^,,/ {print $NF+0; exit} END {print 0}'` —— **awk 的 `exit` 會執行 `END`**，
  所以印完 `1` 又印 `0`，變數變成兩行，`[ "$x" -gt 0 ]` 直接報錯。

**這次沒有新的防呆。** 「掃描時 tag 還沒登錄」本來就有正確的行為：記成 `unknown`
但**保留 uid**，所以事後補得回來 —— 這正是 `MEASUREMENT-STATION.md` 當初
「不丟棄、只標記」那個決定買到的東西。

**附帶完成：`cactus-13-2` 的 tag 已回收。** `535F6417230001` 現在貼在 `cactus-29` 上，
那顆 uid 的最新讀數不再屬於 13-2，`live` 的推導自己就把它判成退役。面板 10/14 的
`ended` 名單因此清空（機制保留，下一次沒有後繼者的結束還是要用它）。面板 10 仍是 25 列。
