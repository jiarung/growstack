## <a id="0904-dli"></a>2026-09-04 — DLI 兩種算法的差異，原因**判斷過兩次都錯**

**症狀** 光譜法日 DLI 長期低於 lux 法，比值 0.51–1.64 逐日擺動。

**原因（第三版，2026-09-07 定案）** **就是上一則的光路遮擋，沒有第二個原因。**
遮擋排除後比值反轉 —— 光譜法現在比 lux 法**高** 40%：

```
台北整日   lux_dli  spec_dli  ratio
09-02       4.00     2.92     0.728   ← 遮擋中
09-03       3.74     1.93     0.515   ← 最糟
09-04       3.62     3.60     0.995   ← 修復當天（11:20 動手）
09-05       3.69     5.09     1.379   ← 第一個完整修復日
09-06       3.51     4.96     1.412   ← 第二個，穩定
```

原始症狀是「光譜法低那麼多」。**它現在不低了，是高的。**

**兩個被推翻的推論，都留著當記錄：**

**第一版（面板說明原文）**：「比值游走本身就是 CAL 尚未定案的證據」。
**不成立** —— `CAL` 在該查詢裡是寫死的常數，`DLI = CAL × ∫S` 對它是純線性的，
錯的 CAL 只會造成固定倍率，數學上不可能造成逐日擺動。

**第二版（2026-09-04 我的判斷）**：「主因是 `lux/54` 在燈下是錯的常數，
純日光與純燈下差 **2.7 倍**，而 84% 的積分 lux 落在 `mixed` cell；光路衰減只是次因」。
**主次顛倒了。** 光路修好後重量同一件事：

| 光源 | 遮擋中（09-04） | 修復後（09-07） |
|---|---:|---:|
| daylight | 1.55 | 1.60 |
| mixed | 0.78 | 1.41 |
| lamp | 0.57 | 1.41 |
| **日光÷燈下的差距** | **2.7×** | **1.14×** |

真正的光譜差距只有 **1.14×**。那 2.7 倍裡絕大部分是壞掉的感測器。

**為什麼會判錯（這才是要記住的）** 遮擋是**角度性**的 —— 日光和燈從不同方向進來，
被擋掉的比例不一樣。所以一個純機構故障，在按光源拆開的表格裡**長得完全像光譜效應**，
而且方向、量級都很有說服力。我當時把兩個原因分開列了，卻沒想到次因會汙染主因的量測本身。

> **一個會隨光源方向而異的故障，可以偽裝成任何「與光譜有關」的結論。**
> 排除幾何因素之前，不要對光譜下結論。

**仍然成立的部分**：`lux/54` 的 54 lm/µmol 確實是為太陽光定的，套在 LED 上沒有物理依據 ——
這是方法本身的性質，沒有改變。改變的是它的**實測影響量級**：1.14× 而不是 2.7×。

**處置** ✅ 症狀已解決。但**絕對尺度仍不可信**：`CAL` 尚未重配，而重配的前提
（通量比回到 6.0 以上）還沒滿足 —— 現行 5.19。見上一則。

## <a id="0907-lux-low"></a>2026-09-07 — lux 法遠低於光譜法：是預期物理，不是故障

**症狀** 光路修好後比值反轉並穩定：lux 法比光譜法低約 **1.41×**（09-05 1.379、09-06 1.412）。
與 [2026-09-04 的 DLI 那則](#0904-dli) 是同一件事的後續 —— 那則問「為什麼光譜法低」，
這則問「為什麼現在反過來」。

**證據 —— 燈的實測光譜（2026-09-05 19:00–20:00，純燈下，counts ÷ R）**

```
f415 14.0%   f445 28.3%   f480  7.1%    → 藍 415-480  49.4%
f515  9.1%   f555  9.1%                 → 綠 515-555  18.2%   ← 凹陷
f590 12.1%   f630 10.2%   f680 10.0%    → 紅 590-680  32.3%
```

藍＋紅雙峰、綠光凹陷 —— 標準園藝 LED。

**原因** `lux` 是明視覺加權，峰值 555 nm 綠光；這顆燈刻意避開綠光（對光合貢獻低、對人眼卻最亮）。
所以**同樣的光子數，它產生的流明比太陽少**，而 `lux/54` 的 54 lm/µmol 是為太陽光定的。

從八個通道的光譜形狀直接推算，不經過 `CAL`：

```
燈       明視覺加權 ÷ 光子加權 = 549.7
D65 日光 同一指標              = 672.2
→ 預測 lux/54 在燈下低估 1.22×
→ 實測 spec/lux 在 lamp cell    1.41×
```

**同方向、同量級。** 一個從光譜形狀算出來的預測，對上一個直接量到的比值。

**剩下的 1.41/1.22 = 1.16（約 16%）拆不開**，三個已知來源都指向同一件事：
`CAL` 已失效（07-16 擬合，之後經歷 07-22 與 08-11）、感測器還差 20% 未歸位
（會讓 S 偏低，也就是讓 1.41 **偏小**）、以及 AS7341 只有 8 個窄帶、
`Σ(counts/R × λ)` 只是對真實光譜的粗略近似。分開需要 Photone 地面實測。

**處置** ✅ 症狀已解釋，**不需要修**。這是方法本身的性質：
`lux/54` 在 LED 下沒有物理依據，而燈佔了 99% 的積分光量。

順序不可反：**先把感測器角度調回通量比 6.3 以上，再用 Photone 重配 `CAL`。**
光路沒回到基準就重配，等於把光學損失直接烤進 `CAL`
（`broker/PPFD-CAL-ROUTINE-PLAN.md`）。

**衍生出的兩條通則已升級到上層文件**，不重複在此：
- 「故障若與你正在變動的量相關，它會長得像結論」→ `MAINTENANCE.md` 失效類型 6
- 「原始 counts 不是光譜」「daylight cell 是 54 lux 曙光」→ `QUERYING.md` traps 5、6

## <a id="0909-scale-zero"></a>2026-09-09 — 秤的零點在漂，`used%` 的訊噪比小於 1 ♻

**症狀** OLED 上的耗竭% 看起來不對：多數盆停在 20–30%，而 `cactus-13-2` 顯示 **120%**
（超過定義上限）。使用者的原話是「損耗的顯示怪怪的」。

**證據** 相鄰秤重場次之間、同一批植物的重量變化中位數在 **−25.6 ~ +18.2 g** 之間來回跳，
而且符號交替。決定性的一筆：

```
08-25 11:14 → 08-25 20:32   同一天隔 9 小時   12 株全部變重，最少的也 +5.1 g
```

仙人掌不會在 9 小時內集體增重。四個相鄰場次出現這種情形（08-08→10、08-25 當日、
08-29→30、09-05→06）。空秤讀數（`quality=empty`，沒有盆在上面）本身也在
**−10.2 ~ +11.2 g** 之間漂，同一個量級。

**原因** 加性零點漂移，**與盆重無關**：

```
< 300 g 的盆 (n=33)   +10.5 g
> 800 g 的盆 (n=10)   +11.0 g
合併：增重 = +11.94 g − 0.0012 × 盆重     r = −0.08
```

279 g 的盆和 1221 g 的盆增一樣多。四倍的土不吸四倍的水，所以**不是質量**。
零點是在序列埠手動 tare 一次、存進 NVS，之後永不重取（`src/sensors.cpp:315-320`）。

**兩條被測試否定的假說**（都由使用者提出，都值得記下來）：

- **雨。** 四個異常場次有三個在雨天，看起來很像。但雨量單獨的 R² 只有 **0.02**，
  加進模型後係數 +0.069 g/mm、R² 完全不動（0.54 → 0.54）。雨天只是「冷且濕的日子」。
- **土/素燒盆吸空氣中的水。** 被上面的盆重測試否定 —— 那是真實質量，會隨土量縮放。

**未能分辨的**：溫度與濕度 `corr = −0.96`，統計上分不開（`dT` 單獨 R²=0.54，
`dH` 單獨 0.45）。所以「秤在量溫度」這個說法**不能宣稱** —— 只能說零點在漂。
（我一度這樣宣稱過，是過度解讀。）

**為什麼顯示會歪** 分子是兩個不同場次相減，帶 ±11–15 g 噪音；而典型分子只有約 10 g。
在 33–45 g 的 span 上，那是 ±34 個百分點的顯示噪音。**50% 以下基本上沒有內容；
85% 以上才是訊號。**

**處置** ♻ **零點漂移本身未修**，它每一次量測都會再來。三條路已排序，尚未執行：
每場次先記一筆空秤讀數（幾乎全消，只需改 Node-RED 流程，不動韌體）／
溫度回歸修正（約消 54%，可回溯補歷史）／`sat_g` 改用次大值（只治標的一半）。

**被否定的處置**：曾提議改韌體自動重取零點。使用者要求先有更強的證據，是對的 ——
加性偏移可以完全在伺服器端修掉，不需要動韌體。

## <a id="0911-invisible-watering"></a>2026-09-11 — 澆了水但沒再秤，那次澆水就不存在 ♻

**症狀** 使用者 09-10 傍晚澆了全部植株，隔天 `該澆水了嗎` 仍有兩株顯示
「距上次澆水 11.8 天」，其中 `cactus-13-2` 標成 **● 該澆水**（耗竭 137%）。

**證據** 09-10 那場是「秤 → 澆 → 再秤」交錯進行的：

```
17:55:54   800.2  cactus-08     ┐
18:00:24  1756.7  cactus-14     │ 澆水前
18:03:41   701.7  cactus-13-1   │
18:05:13  2313.0  cactus-12     │ ← 只有這一筆
18:07:42   690.4  cactus-06     │
18:09:05  1540.2  cactus-13-2   ┘ ← 只有這一筆
────────────────────────────────
18:12:37   760.7  cactus-06     +70.3  ✓
18:13:27  1963.8  cactus-14    +207.8  ✓
18:25:45   840.2  cactus-08     +40.2  ✓
```

`cactus-12` 與 `cactus-13-2` 拿到了「澆水前」那一筆，**沒有拿到「澆水後」那一筆**。
`cactus-13-1` 也漏了同一輪，但它 09-11 15:23 被秤到，`+81.2 g` 當場補上。

**原因** 澆水是**推論**出來的，不是記錄下來的：`JUMP = 10.0`，相鄰兩次秤重之間
增加超過 10 g 才算一次澆水（`daily.json` 面板 10，與面板 2 的速率過濾、面板 11
的場次偵測同一個常數）。**沒有第二個讀數就沒有跳躍可看。**

系統沒有「澆水事件」這種東西可以記 —— 它只有重量。

**處置** ♻ **不是程式缺陷，是量測方法的邊界，而且每次跳過重秤都會再發生。**

重秤即可，錨點從 90 天歷史算，不需要當場補。`cactus-12` 於 09-11 15:47 重秤
2375.5 g（比 09-10 那筆高 62.5 g），耗竭當場從 84% 歸零。`cactus-13-2` 待重秤。

⚠ **但錨點會被記在「揭露它的那一筆」上**，不是實際澆水的時刻。`cactus-12` 因此
顯示 `days = 0.002`，而真正的澆水在 21.5 小時前 —— 少算約 0.9 天。這是方法本身
的性質，補一筆假讀數去修它會違反「raw 從未被改寫」（2026-09-08 已為此 revert 過
一次 backfill）。

**為什麼這不是可以忍的小事**：後果不是中性的。漏掉的那盆會慢慢爬到「該澆水」，
你照著面板澆，**就會澆第二次**。這個系統存在的理由正是要避免那件事。
