## <a id="0803"></a>2026-08-03 — Open-Meteo 間歇 503，每小時輪詢沒有重試

**症狀** 天氣面板每天只有 3–10 個點而不是 24 個，之後整整 11 小時完全停擺。

**證據** 07-30..08-03 期間，每天 24 次輪詢有 16–21 次失敗。同一個 URL 隨手打都回 200，
所以是輪詢當下的上游不穩，不是服務中斷。

**原因** `inputs.http` 在一個 interval 內不會重試，所以每次失敗就損失整整一小時。

**處置** 改為每 5 分鐘輪詢。這是**重試預算，不是取樣率** —— 點的時間戳來自 payload 的
`current.time`，只每 900 秒前進一次，所以同一格內的額外輪詢只是覆寫同一個點，零儲存成本。
同時新增 `deadman-weather-stale`（>1h）—— 那 11 小時的中斷是**用眼睛發現的**，因為沒有任何東西在看。

**不要「還原」舊行為。** → `broker/README.md` 燈控段、`FLOWS.md` B 段。

## <a id="0814"></a>2026-08-14 — I²C 卡死回 0xFFFF，與真飽和長得一模一樣 ♻

**症狀** `65535` counts 出現，無法分辨是真的被光打滿，還是 AS7341 卡在 I²C 上不回應時
driver 讀回來的 `0xFFFF`。

**證據** 真飽和時各通道會依自己的響應度**依序**爬到滿格；卡住時會出現
f415 滿格而 f555 只有 16,157、下一筆完全倒過來，以及 1084、3203 這類**跨通道重複**的垃圾值。

**原因** driver 在 I²C 無回應時回傳 `0xFFFF`，與合法的滿格值無法從數值上區分。

**處置** ♻ **會復發，自 08-14 起反覆發生。**
分辨方法是 `spectrum_read_ms`。DLI 面板的查詢因此必須濾掉 `65535`，
否則這個故障會在日積分裡渲染成一根巨大的 PPFD 尖峰。
斷電修復（Tapo 插座 `sensor`，192.168.50.52）；偶爾會自己好，最久觀察到 51 分鐘，但不可靠。

## <a id="0831-write"></a>2026-08-31 — 寫入回報成功卻什麼都沒存

**症狀** 查詢正常、`compute-k-models.sh` 印「10 bucket(s) written」，而 bucket 裡跨 1970–2200 全空。

**證據** 同一個 token，只差 `-i`：

```
無 -i   exit=0   落地 0 點
有 -i   exit=0   落地 1 點
```

**原因** `docker exec` **不加 `-i` 不會接上 stdin**，`influx write` 讀到 EOF 立刻結束、
寫入 0 筆，然後 **exit 0**。讀取路徑不受影響（Flux 是以參數傳入），所以整條管線看起來很健康。
同一個常數也存在於 `ack-k-hold.sh` —— `--accept` 會靜默地什麼都不做。

**處置** 已修。`influx delete` 有鏡像陷阱：**匹配不到任何東西的 predicate 也 exit 0**，
所以刪除前後都要數。→ `MAINTENANCE.md` 失效類型 3。
