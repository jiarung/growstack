_配 [phase-1b.md](./phase-1b.md)。那份講機制,這份是照著做的步驟 —— 與
[overheating-procedure.md](./overheating-procedure.md) 同一個體裁。_

**通過標準寫在看到數字之前。** 這條線記過「迎合性同意」的帳:看到直方圖之後才挑的
標準不是標準。下面每個門檻都附推導,不是拍腦袋。

## 0. 這批修了什麼,以及為什麼需要驗

症狀:同時開 viewer 的 `auto`(每 N 秒 `/observation`)和 `live`(每 250 ms
`/api/aim` → `/thermal`)時,熱像整片讀到 33–43 °C,室溫 24 °C。只開 `live` 正常。

**已證明的因果鏈**(從程式碼讀出來的,不是推測):

1. `/thermal` 原本**一個像素一個 HTTP chunk** —— chunked encoding 每個 chunk 自帶
   長度行與 CRLF,各自一次 socket write,768 顆約 2000 次。
2. httpd task 優先權 5、`core_id` 預設 `tskNO_AFFINITY`;loopTask 優先權 1、釘在
   一顆核上。httpd 可以落到同一顆核把它壓住。
3. `thermal::poll()` **只在 `loop()` 裡**,是唯一會排空 UART ring 的東西。
4. `ChecksumPolicy::REPORT`:校驗失敗的 frame **照樣解碼並發布成真實溫度**
   (`gymcu_parser.cpp:59`)。

**尚未證明的最後一環**:掉 byte 會不會產生**均勻** +8 °C。掉 byte 的自然結果是亂值
(奇數 byte 錯位)或整體位移(偶數 byte 錯位),兩者都不明顯是均勻偏移。**這次要驗的
就是這一環** —— `gap` / `rxerr` 有沒有真的跟那個偏移一起動。

**修法**:(1) 像素輸出併成 ~5 個 chunk;(2) `cfg.core_id = 1 - xPortGetCoreID()`;
(3) 把不變式本身量出來。(1)(2) 只降低機率,**(3) 才是讓「修好了」變成可證偽的東西。**

## 2. 讀懂新的那行

```
[thermal] bytes=N frames=N bad_cs=N bad_hdr=N resync=N dropped=N overwr=N rxerr=N gap=Xms ringpk=Y/4096
```

| 欄位 | 回答什麼 | 怎麼讀 |
|---|---|---|
| **`rxerr`** | **driver 說它掉了 byte** | **唯一決定性的。非 0 = 確定有 frame 是殘缺資料拼出來的,而且已經被當成溫度發出去了** |
| **`gap`** | poll() 最壞間隔(ms) | **餘裕**。其他欄位都只在餘裕用完之後才動 |
| **`ringpk`** | ring 最高水位 / ring 大小 | 同上,從另一個角度 |
| `overwr` | 好 frame 在被取走前就被蓋掉 | 遲到的代理:要兩幀在同一個 pass 完成才會動 |
| `dropped` / `resync` | parser 受損後在找 sync | 下游推論 |
| `timeouts` | 半截 frame 被放棄 | 下游推論 |
| `bad_cs` | **目前什麼都不代表** | 校驗慣例未解,每一幀都失敗。見 `thermal::checksumPolicyName()` |

### 門檻怎麼來的

```
BAUD 115200 8N1        -> 11520 B/s 線速
frame 1544 B           -> 一幀傳輸 134 ms
REFRESH_HZ 4           -> 每 250 ms 一幀(線上 54% 時間在忙)
RX_BUFFER 4096 B       -> 2.65 幀
```

poll() 停擺後 ring 填滿要多久:落在 burst 裡是 `4096 / 11520` = **356 ms**(最壞),
平均速率算則是 `4096 / 6176` = 663 ms。**取最壞的 350 ms 當硬上限。**

| `gap` | 判定 |
|---|---|
| ≤ 100 ms | **通過** —— 3.5× 餘裕 |
| 100–250 ms | 通過但很薄,要記錄,且結論只能做「明顯過/明顯不過」 |
| > 350 ms | **失敗**,byte 已經掉了(`rxerr` 應該同時非 0) |

`ringpk` ≤ 1544(一幀)= poll() 從沒落後超過一幀。`ringpk` > 3000(ring 的 73%)= 貼著
溢位邊緣在跑。

`rxerr` 必須是 **0**。這條沒有灰帶。

## 3. A/B 程序

> **`gap` 和 `ringpk` 是自開機以來的峰值,只升不降。** 所以**不要在兩個條件之間重開**
> —— 那會把比較基準洗掉。正確作法是**負載由輕到重單調遞增**,每加一層看峰值有沒有
> 被推高。沒被推高 = 這一層沒有讓情況變差,這正是要問的問題。

| # | 條件 | 時間 | 記錄 |
|---|---|---|---|
| 3.1 | 開機後**完全不碰**(無 HTTP) | 2 分鐘 | 基準 `gap` —— `loop()` 沒有 delay,預期個位數 ms |
| 3.2 | **只開 live**(viewer 勾 live thermal) | 3 分鐘 | `gap` 有沒有被推高 |
| 3.3 | **live + auto** 同時開 | 3 分鐘 | 同上。**這是修復前會炸的那一格** |
| 3.4 | 維持 3.3,把頭對準室內牆(不是窗簾) | 1 分鐘 | `/thermal` 全幀應回到 25–26 °C |

3.1 就 > 100 ms ⇒ 問題不在 HTTP,在 `loop()` 裡別的東西(`wifiSupervise()` 的阻塞
`WiFi.begin()` 是頭號嫌疑),core pinning 幫不上忙。

3.3 把 `gap` 推過 350 ms 或 `rxerr` 非 0 ⇒ **(1)(2) 不夠**,下一步是把 `poll()` 搬進
自己的 task。**優先權必須反過來** —— `beat` 用 priority 1 是為了不搶別人,`poll()` 要
的是不被搶,得高於 httpd 的 5。照抄 `beat` 會看起來修好了但什麼都沒修。見
`tasks/todo.md`。

### 3.5 驗最後一環(這才是重點)

3.4 回到 25–26 °C,**而且** 3.3 全程 `rxerr=0` / `gap` 低 ⇒ 因果鏈補完:starvation 沒了、
溫度也對了。

若溫度對了但 `gap` 從頭到尾都很低(修復前的數字拿不到了)⇒ 只能說「現在是好的」,
**不能宣稱已證明 +8 °C 就是 starvation 造成的**。要補證據的話,唯一乾淨的方法是刷回
`1fb63f0` 重現一次 —— 值不值得由你決定,我的看法是不值得。

## 4. 同時在跑的第二條線:PSRAM 碎片化

**不同的故障,同一次燒錄。** 症狀:板子放久之後 snapshot 變頓、最後沒反應,重開才好。
機制在 `/observation` 的 `ps_malloc`(`endpoints.cpp`):先配新的、才放舊的,兩塊
200–400 KB 必須同時存在,而每張 JPEG 大小都不同 —— 沒有洩漏,但會碎片化。

```bash
tools/s3cam/health_soak.py http://<ip> 60 tmp/health.csv
```

開機後先記一次基準,然後掛著。**要看的是 `psram_free` 和 `psram_largest` 的落差**,
不是任何一個單獨的數字:前者可以維持好幾 MB,而後者一路掉向一張 JPEG(200–400 KB)
的大小 —— 那就是確診。

### 下次發作時,**重開之前**先跑這三行

```bash
IP=<ip>
time curl -s -m 30 http://$IP/health                                                          # (a)
time curl -s -m 30 -o /dev/null -w '%{http_code} %{size_download}\n' http://$IP/capture       # (b)
time curl -s -m 30 -o /dev/null -w '%{http_code} %{size_download}\n' http://$IP/observation   # (c)
```

`/health` 是乾淨探針:只讀快取過的 `sensorPid` 和兩個 microsecond 級 spinlock,
**完全不碰相機鎖**。`/capture` 直接送 fb,**沒有** `ps_malloc`;`/observation` 有。

| 觀察 | 結論 |
|---|---|
| (a) 也卡住 | httpd task 或網路。ESP-IDF httpd 所有 handler 跑在同一個 task,一次一個 —— 查 `/stream` 是不是被誰開著沒關 |
| (a) 秒回,(b) 正常,(c) 慢或 500 | **碎片化確診**,兇手是那個 `ps_malloc` |
| (a) 秒回,(b) 跟 (c) 一樣爛 | 相機路徑。再打 `/power`,沒在拍照卻顯示 idle 倒數 = 0 ⇒ `inUse` 洩漏 |

## 5. 這批**沒有**修到的(不要誤以為有)

- **`rxerr` 只計數,不影響信任。** driver 說掉了 byte,那一幀還是會被發布成真實溫度。
  要不要據此丟棄是**政策變更**,跟 ChecksumPolicy 一起做。
- **`/thermal/raw?hex=1` 仍然是一個 byte 一個 chunk**(1544 個)。那是 debug 熱像損壞時
  會打的端點 —— **在最不該製造 socket write 風暴的時刻製造風暴。** 驗收期間不要打它,
  真要打就在 `live` 關掉的情況下打。
- **`endpoints.cpp` 還有約 30 處 `snprintf` → `send(m)` 沒有夾制。** `clampLen()` 已經
  在檔案裡,只用在被改到的三處。
- **checksum 慣例仍未解。** `bad_cs` 會等於 `frames`,那是預期的,不是警報。

### 2026-09-29:儀器自己的缺陷,上機第一天就抓到

```
poll_gap_max_ms: 7          ringpk: 4072/4096      rx_errors: 285
bytes_dropped: 1164         overwritten: 1         uptime: 1374s
```

`gap=7ms` 和 `ringpk=4072` 不可能同時是穩態:7 ms 在 11520 B/s 下只累積 80 bytes。
20 秒 / 80 幀之後再取樣,`rxerr` / `dropped` / `ringpk` / `overwr` **四個全部凍結**,
只有 `bytes_seen` 和 `frames_ok` 在走。

**全是開機殘留。** `thermal::begin()` 在 `main.cpp:77` 開埠,模組立刻開始送;但 `loop()`
要等 setup() 把相機(含 4077 bytes 的 AF 韌體走 SCCB)、WiFi、NTP 都做完才會跑 —— 那是
好幾秒,而 ring 只裝得下 356 ms。**每一次開機 ring 都會在沒有人排空過的情況下溢位。**

於是兩個最有用的計數器被一個開機假象永久釘死,再也報不出 runtime 餘裕 —— 而那正是
它們被加進來要做的唯一一件事。**修法**:第一個 poll() pass 把累積的 bytes 丟掉(那些
byte 依構造就是碎片,ring 把中間吃掉了)而不是餵給 parser,然後把峰值與 `rx_errors`
歸零,開機數字移進 `boot_discarded` / `boot_rx_errors` 兩個獨立欄位 —— 不藏,只是隔離。
**這個修正尚未燒錄。**

`/observation` 的 `ps_malloc` 需要一塊完整的 JPEG 空間 —— 平衡點若低於那個門檻,症狀
就會長得跟碎片化一模一樣。A/B 的 phase C 會回答。

### 2026-09-29 12:44–12:53:A/B 跑完,結論是**假設錯了**

計數器(第 3 節的程序,中間沒有重開):

```
                      gap  rxerr  dropped  overwr  tmo  resync   frames    heap
A idle (90s)            7    285*    1164*      1*   0       0    +350    212.9K
B live 4Hz (180s)       7    285     1164       1    0       0    +712    208.3K
C live+auto (180s)      7    285     1164       1    0       0    +714    208.3K
request failures: live=0 auto=0                    * 開機殘留,三段全程凍結
```

`gap` 三段都是 **7 ms**,對 350 ms 的硬上限是 50× 餘裕。一幀沒掉,frame rate 全程 ~3.9 Hz。
heap 在負載下降到 208.3K 後**打平**,`psram_largest` 在 5.77–6.16 MB 擺盪(`/observation`
持有 JPEG 的正常呼吸),離 200–400 KB 的危險區還有一個數量級。

畫面本身(第 3 節原本漏掉的那一半 —— 只量串流健康度不量 payload,而症狀講的是溫度):

```
IDLE        Ta=32.84  min=31.85 max=48.80 mean=36.61(sd 0.09)  L/M/R=37.8/35.2/36.9  chk=+0.96
LIVE+AUTO   Ta=32.77  min=31.77 max=48.89 mean=36.65(sd 0.10)  L/M/R=37.9/35.3/37.0  chk=+0.84
IDLE again  Ta=32.82  min=31.66 max=48.79 mean=36.72(sd 0.14)  L/M/R=37.9/35.4/37.1  chk=+1.14
```

條件之間的差是 0.04–0.11 °C,條件內部的幀間 sd 是 0.09–0.14。棋盤格在兩次 IDLE 之間的
變化(+0.96→+1.14)還大於 IDLE 對 LIVE+AUTO。

**可以說的是:排除了 8 °C 量級的負載效應** —— 那正是要查的症狀。**不能說「毫無影響」**:
最大的 0.11 並不小於 0.09/0.10,而且 sd 不是顯著性檢定(平均值的不確定度比 sd 小
1/sqrt(n))。這是 idle→load→idle 的序列設計,顯示的是小幅漂移,不是嚴格的等價性檢定。

#### 結論,分開講

1. **本韌體在 live+auto 下沒有偵測到 runtime starvation。** 「一幀沒掉」應寫成「未偵測
   到遺失」—— 幀計數本身不構成完整的期望幀數核對。而且**開機時溢位的那批 byte 是餵給
   parser 的**,在 checksum 慣例未知的前提下沒有任何獨立的幀對齊驗證,所以這排除的是
   「HTTP 造成的 runtime starvation」,不是開機損壞、也不是所有 serial/framing 成因。
2. **但這不等於「修復解決了 starvation」** —— 舊韌體沒有這些計數器,沒有 before 數字。
   有可能舊韌體的 `gap` 也一直是 7 ms。要補只能刷回 `1fb63f0` 重現,判斷是不值得,
   但**不能當作已驗**。
3. **+8 °C 偏移與 starvation 無關。** 零負載下就在,而且兩種負載下數值一致。原本那條
   因果鏈(chunk 風暴 → 餓死 poll() → 掉 byte → REPORT 把殘骸當溫度發布)**最後一環
   是錯的**。程式碼確實變好了(socket write 2304 → 15 是真的),但打的是錯的靶。
4. **使用者原本的觀察(auto+live 一起開就壞)在本韌體上重現不出來。**

#### 唯一站得住的一句

**一面相信在 25.8 °C 的牆,貼近填滿視野,讀 35.40 °C。** 其餘都是尚未識別的模型。

#### 為什麼這不太可能是反射

牆若 ε<1 會反射較熱的環境(熱像頭在 5-10 cm 處),所以「比 Ta 冷的面不可能讀得比 Ta 熱」
**這句話是錯的,撤回**。但算一下量級就知道反射解釋不了:

```
需要的輻射過量           (35.4C)^4 - (25.8C)^4 = 1.076e9 K^4
若全部來自 45.5C 的機頭  需要反射佔比 0.463  =>  牆的 eps <= 0.54
eps=0.90、機頭佔滿整個反射半球(上界)  ->  27.95 C
eps=0.90、視因子 0.03 / 0.33(實際)   ->  +0.07 / +0.71 C
```

一般油漆牆 ε≈0.9,所以反射最多解釋 1 °C 以內。**除非那面牆異常低發射率或有光澤。**

#### 這一節**不**成立的東西

見〈撤回清單〉。特別是:`mean - Ta = +5.93` 這個「恆定」只跨了 4.76 °C 的 Ta,而且
風扇同時冷卻了感測器與它所看的東西,所以 corr=0.998 是**自製的共變**,對任何假設都
沒有鑑別力。

## 〈撤回清單〉

_錯的判讀留在這裡而不是刪掉:下一個人會重新想到同一條,知道它為什麼不成立能省一輪。_

| # | 撤回的主張 | 為什麼不成立 |
|---|---|---|
| 1 | **chunk 風暴餓死 `poll()` → 掉 byte → +8 °C 偏移** | A/B 證明零負載下偏移就在,且三種負載下 payload 無差異。程式碼改善為真(socket write 2304→15),因果鏈最後一環為假 |
| 2 | **視野是瞎的 / 鏡口被不透明物擋住** | 冰水在 8 cm 讀 6.90(mean-Ta = -23),感測器響應正常。支持它的 `d(mean)/d(Ta)=0.907` 是風扇同時冷卻兩者造成的自製共變,無鑑別力 |
| 3 | **操作者在視野裡造成 34-37 °C** | 牆貼近測試(D)操作者在機後,仍讀 35.40 |
| 4 | **增益 = 1.31** | 由「牆」與「玻璃壺」兩點推出,但玻璃在 8-14 µm 不透明,量到的是**外壁**,其溫度未知。兩點中一點不成立,直線不成立 |
| 5 | **「比 Ta 冷的場景不可能讀得比 Ta 熱」** | ε<1 的面反射較熱環境就可以。量級上反射只值 ~1 °C(見上),所以結論改成「反射解釋不了」,不是「不可能」 |
| 6 | **TA_SHIFT 從 8 變 0** | K^4 算術本身正確(1.076e9 vs 1.081e9),但那是**輻射單位下的數字巧合**。Melexis 的式子裡 Tr 乘上 `(1-eps)/eps`,eps=0.95 時 9.8 °C 的 Tr 誤差只產生 **+0.53 °C**,差 18 倍,而且**提高 Tr 會降低**算出的 To —— 方向也是反的 |
| 7 | **「不是固定偏移也不是單純增益」** | 這個結論靠 #4 的玻璃壺點,而該點已撤回。只有一個有根據的點時,增益模型與偏移模型都無法被否證 |
| 8 | **`mean - Ta = +5.93` 是「比 die 高 5.9」** | `Ta` 是 MLX90640 自己的環境感測器,**不是** ESP32 的 `die_c`。同一段期間 `mean - die` 從 -8.26 變到 -1.51 |
| 9 | **「一幀沒掉」** | 應為「未偵測到遺失」。幀計數本身不構成完整的期望幀數核對 |
| 10 | **payload A/B「完全沒有影響」** | 條件間最大差 0.11 並不小於條件內 sd 0.09/0.10;而且 sd 不是顯著性檢定(平均值的不確定度小 1/sqrt(n))。可以說的是「排除了 8 °C 量級的負載效應」,不是「無影響」 |
