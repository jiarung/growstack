# 澆水指標 —— 持續進行的分析

**目前結論（2026-09-22）：現有指標的分母錯了 1.7 倍，已換。** `減重/span` 的 `span`
是「歷史最大回落」，比一盆真正停止失水時的總失重 A 大 1.7 倍，所以小盆到平台期時
只顯示 ~47%，80/100 門檻永遠不亮 —— 16/20 盆因此晚澆中位 1.1 天，大盆反而早澆。
`fit-plateau.py` 現在替每盆擬合它自己的乾燥曲線 `L(t) = A(1−e^(−t/τ))`，
面板 10 與 OLED 的分母改用 A（`basis = 平台`），**100% 從此等於「已經不再掉了」**。
韌體零改動。

**盆內標準化站得住**（AUC 0.727 → 0.769，對場次洩漏與前瞻驗證都穩健）。
**扣裸土蒸散在現行對照盆下不可用**：對照盆速率主要是它自己的乾燥階段
（`r = −0.69`），而那個階段與植株獨立（`r = +0.04`）—— 減掉的是噪音。
要它可測，對照盆得改成恆定濕度（秤→補水到固定重量→補秤）。

每週一 01:30 `plateau-review-reminder.sh` 重擬合並提醒做 recall。

重跑（任何時候，不需參數）：

```bash
./analyze-et.py --index --band 150,2600
./analyze-et.py --index --band 185,245     # 只看同尺寸的一群
```

離線測試：`../test/broker/test_analyze_et.py`。

## 問的是什麼，以及這個問法的限制

OLED 和面板 10 要顯示一個「這盆該不該澆水」的數字。候選指標用
**AUC** 評分：隨機抽一筆「之後 36 小時內被澆」和一筆「沒被澆」，指標排序正確的機率。
0.5 = 亂猜。

**基準是你的判斷，不是植物的需要。** 所以這些數字只能拿來**比較指標之間的優劣**，
不能讀成「這個指標是對的」。一個純粹重現你澆水節奏的指標在這裡也會得高分 ——
這正是每張表都同時按「距上次澆水天數」切開的原因：日曆自己的分數在三天後崩掉
（低於亂猜），而那正是真指標必須證明自己的地方。

每筆樣本 = 連續三次秤重、中間沒有澆水。三次而不是兩次，因為速率需要兩次、
速率的變化需要三次。錨點用「上次澆水後的第一筆」，和 OLED、面板 10 的定義一致。

## 已確立

### 1. 盆內標準化（2026-09-20，已驗證，可部署）

```
指標                          混池    盆內
減重/span                    0.727   0.769
距上次澆水天數                  0.723   0.780
減重/澆水時重量                 0.677   0.693
乾燥速率 g/day                0.580   0.614
減速 g/day²                  0.616   0.609

以盆分組交叉驗證(200 折,測試盆完全不參與)
減重/span        中位 0.772   IQR 0.735-0.808
```

介質比例、品種蒸散能力、盆材、持水量 —— **每一個都是每盆常數，每一個都沒量過**。
混池比較是拿 A 盆和 B 盆比，盆內標準化是拿 A 盆和它自己比，常數自己約掉，
從頭到尾不需要知道它們是多少。

**使用者不需要去統一介質或記錄品種。** 這是這整份分析最有實用價值的一條。

**穩健性（2026-09-22 補測，兩個都可能讓分數虛高）**

```
以『日』分組 vs 以『盆』分組交叉驗證     差 +0.013   成批澆水的標籤相關影響有限
前瞻 z（只用這筆之前的樣本算平均/標準差）  0.728 → 0.698   部署時看得到的版本仍遠高於亂猜
```

### 2. 混池會把訊號反轉（Simpson's paradox）

減速這個指標：

```
混池     0.374      看起來是「反向」
盆內     0.64       16/17 盆方向一致(符號檢定 p = 0.00014)
```

同一批資料、同一個指標，結論相反。`test_analyze_et.py` 有一個刻意構造的最小反例，
避免未來重構時把標準化拿掉而報告看起來依然合理。

### 3. 日曆在三天後失效

```
指標                  1-2d    2-3d    3-5d
減重/span            0.880   0.716   0.653
距上次澆水天數          0.600   0.784   0.660
減重/澆水時重量         0.657   0.744   0.520
```

「距上次澆水天數」整體 0.723 的分數大半來自簡單的案例（剛澆完，誰都知道不用澆）。
真正需要判斷的區間，它不比丟銅板好多少。

而 `corr(減重/span, 天數) = +0.189` —— 現有指標本來就幾乎和日曆無關，
它不是日曆的改裝版。

### 4. 分母：從「歷史最大回落」換成「擬合的平台期失重」（2026-09-22，已部署）

使用者的觀察：「很多盆栽（如 cactus-10）我澆水時其實已經不太減重了，再等下去要開始
掉植株重量」。量化：

```
cactus-10   τ = 0.7 d → 90% 平台在 1.6 天    實際澆水中位 3.5 天    晚 1.9 天
16/20 盆晚澆,中位 +1.1 天;大盆(13-3/13-1/14)反而早 1.4–13 天(跟著小盆成批)
```

根因是分母。`span` = 歷史最大回落，混進了換盆前、極端週期、或植株還沒放進去時的
數字；每盆擬合的 A 才是「這盆停止失水時掉了多少」：

```
                    平台期時顯示    ≥80% 的比例
span(舊)               47%            9%
A(擬合)                85%           53%        n=148 個平台期區間
```

`fit-plateau.py` 每週重擬合、寫進 `plant_plateau`；面板 10 與 publisher 讀同一個 A
（`basis = 平台`），不各算各的。擬合不到的盆（歷史 <3 循環、τ 撞格點上界、rmse > A/2）
沿用舊 span —— 寧可分母偏大也不要一個假的 A。cactus-14（1.8 kg）第 8 天還在掉，
它的曲線要用週來量，暫時擬合不到。

**「known our plant」**：每盆的 (A, τ) 就是它的指紋。τ 從 0.3 到 3 天，同一個日曆
對它們的意義完全不同 —— 這正是為什麼「距上次澆水天數」在三天後崩掉。

## 已否證（留著，因為它們都很像好主意）

| 想法 | 結果 | 為什麼 |
|---|---|---|
| 乾燥速率當指標 | 盆內 0.614，2-3d 只有 0.479 | 速率沒有除以持水量，量到的是「這是小盆」不是「這盆乾了」 |
| 加速度 / 速率比 | 混池看起來反向；盆內 0.61，固定 `減重/span` 後無增益 | 微分放大噪音：讀數 σ≈3.5 g → 速率 σ≈5 → 加速度 σ√6≈8.6，而日間減速只有約 5 g/day² |
| ETA「還要幾天用完」 | 分層看 0.80/0.76 很漂亮，但固定 `減重/span` 後是 0.304/0.495/0.619 | 方向在區間之間翻轉 = 過度配適 |
| 同儕中位速率當環境因子 | 0.788，比基準好 | **洩漏**。68% 的澆水發生在「一天澆 ≥8 盆」的日子，它在預測澆水日程不是植物需要 |
| 用 `質量^(2/3)` 縮放裸土蒸發 | 0.743 → **0.541**，大幅變差 | 擬合出來的係數中位 0.16，這個公式給 1.13 —— **扣了 7 倍**。形式對（corr +0.64），尺度錯 |

| 扣裸土蒸發，係數由該盆歷史擬合 | 6 個對照區間 +0.041 (p≈0.10) → **8 個區間 −0.017** | 見下節：不是資料量，是對照盆設計 |

倒數第二條的教訓：**那個失敗看起來像「對照盆沒用」，其實是我把係數猜錯了。**
所以 `analyze-et.py` 一律從該盆自己的歷史擬合係數。

最後一條的教訓更大：**修好係數之後它還是不能用，而且原因在最早的分析裡就講過**
（「把這盆當天氣需求時鐘用是錯的 —— 它同時混了天氣和它自己的含水階段」），
後來被一個 +0.041 帶偏收回了。那個 +0.041 是噪音。

## 扣掉裸土蒸發：為什麼現行對照盆做不到

### 前提有一半成立

```
盆內 corr(該盆速率, 對照盆速率)    中位 +0.375,  12/14 盆為正 (p = 0.0065)
```

對照盆和植株盆確實一起變快變慢。但**一起變的是什麼**才是問題。

### 對照盆的速率是它自己的時鐘

```
對照盆區間                g/day   距它自己上次澆水
09-12→09-13               28.8        0.7 d
09-13→09-14                3.3        1.5 d
09-14→09-15                8.3        3.0 d
09-20→09-21               28.1        1.0 d
corr(速率, 距上次澆水天數) = −0.69
```

澆完隔天 28 g/day，三天後 3 g/day —— 和植株盆一模一樣的形狀（n=8 個區間）。

第一個懷疑是「對照盆和植株在同一批澆水節奏上，所以兩個時鐘是同一個」。**不是**：

```
corr(對照盆距上次澆水, 植株距上次澆水) = +0.041     n=144
corr(對照盆速率, 標籤)                = −0.002
```

對照盆在自己的節奏上（09-12 / 09-17 / 09-20 澆，都不是成批日）。它的速率被自己的
階段主導，而那個階段和任何植株的階段幾乎獨立 —— 所以修正項 `ctrl × b × dt` 減掉的，
對每一盆植株而言是一個**獨立時鐘**，也就是噪音。這比「共享時鐘」更糟：共享時鐘至少
還帶標籤資訊，獨立時鐘什麼都不帶。

（先前記的「被扣掉那一塊 AUC 0.417」：那是 `depl − depl_et` 經盆內標準化後的分數，
n=140，與 `corr(ctrl, 標籤) = −0.002` 並不矛盾 —— 每盆的 `b` 和 `dt` 讓它在盆內
有了結構，但那個結構不是植株的狀態。）

### 三種形式在相同樣本集上全部變差

```
b = 每盆留一法擬合，clip 在 0（現行）   −0.017
b = 每盆擬合，不 clip                 −0.009    ← clip 有一點向下偏，但不改變結論
b = 全體共用一個                       −0.034
b = 1 / 面積猜測                      −0.15
```

### 樣本從 6 變 8 就翻轉符號

```
6 個對照區間   +0.041   置換 p≈0.10
8 個對照區間   −0.017
```

Codex 的判讀：每盆 `b` 由 5–9 個點擬合、而 `ctrl` 只有 6–8 個相異值，
一兩個新值就是高槓桿點，0.058 的擺動是**噪音尺度**。這件事印證驗收門檻設對了 ——
置換檢定和「做不了時間切分」兩道關卡在我把它當成果之前攔住了它。

### 要它能用，該改的是硬體不是模型

對照盆得改成**恆定濕度**。協定：**先秤、再補水到固定目標重量、等排水停了再補秤一次**
（秤→補→秤，補水前的讀數是這段的終點，補水後的是下一段的起點）。那時它的速率
**主要**是「今天的天氣讓這塊土蒸發了多少」，沒有累積的乾燥階段 —— 但補水精度、
表面剛濕的暫態、間隔長短仍會進來，所以它是「更像天氣」，不是「等於天氣」。
`analyze-et.py` 會印 `control rate vs its OWN days-since-watering`，`|r| > 0.5` 就警告
—— 那一行是判斷對照盆有沒有改好的依據。

改好之後 `ctrl × b` 也不會自動成立：仍要前瞻（或留出區間）驗證。Codex 估計
**≥ 20 個對照區間**才夠。

## 下一步

1. ~~把盆內標準化落到面板~~ → **已用更直接的方式做完**：換分母為每盆擬合的 A，
   效果等價於「相對於這盆自己」，而且 100% 有物理意義（停止失水），OLED 不用改。
   盆內 z 分數留作分析工具。
2. **對照盆改協定**：每場次秤→補水到固定目標（例如 230 g）→補秤。哪一天秤仍然
   彈性；間隔長短會影響速率估計的噪音（越長越穩），但不再影響它的乾燥階段。改了之後
   `analyze-et.py --index` 的 `control rate vs its OWN days-since-watering` 應該掉到
   |r| < 0.5，那之後再累積 ≥ 20 個區間才談修正。
3. **不改對照盆的話，它仍然有用**——但用途是原本的問題（裸土 vs 植株誰乾得快）、
   場次零點的共模參考、異常盆偵測。不是澆水指數。

## 已知限制：循環論證

標籤是你的決定，而 OLED 從 2026-08-18 起顯示 `減重/span` 給你看。
一個你看得到的指標，部分是在預測你自己。

```
                   OLED 顯示之前    之後
減重/span            0.643        0.735    (+0.093)
天數(對照,兩期都看得到)  0.795        0.764    (−0.032)
```

方向符合循環論證，但前期只有 29 筆，CI [0.42, 0.85]，置換 p = 0.168 —— **量不出來**。
能說的是：在唯一非循環的視窗裡它仍有 0.643 —— 這個分析裡的訊號不完全由
「OLED 顯示之後」解釋；但標籤仍是園丁行為，循環的程度沒有量出來。
`analyze-et.py --index` 的 C2 節每次都印這張表；前期資料不會再多，
這條限制會一直在。

## 資料衛生（這些錯誤各犯過一次）

- **`quality == "ok"` 不是可選的。** 量測站已經把「刷了標籤但盆沒上秤」標成 `empty`，
  人工刪除的標成 `deleted`。讀原始序列會把它們重新發現成「負重量」，
  而且中位數視窗跨過去會**憑空生出一次不存在的換盆**（2026-09-19 就發生過，
  報告說 `cactus-23` 從 262 g 掉到 119 g，實際上它從沒低於 240 g）。
- **換盆是 id 換人，不是重量階躍。** `cactus-05` → `cactus-05b`。在同一個 id 內找階躍
  會一無所獲並回報「從沒換過盆」。退役是推導的：有後繼者，或在面板 10 的
  `ended` 名單裡（果凍化的盆沒有後繼者，只有那份名單知道）。
- **材質推導不出來**，在 `pot-materials.json`。未列 = 塑膠。猜它的代價是重跑整輪分析。
- **秤的零點每場次會漂 ±6 g**，加性、與被秤物重量無關（`corr(增重, 盆重) = -0.03`）。
  盆間比較用同場次中位消掉它；盆內時序比較不能這樣做（會把乾燥訊號一起減掉），
  改用盆內標準化。
