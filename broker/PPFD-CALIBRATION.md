# PPFD 校準 — 現場指引

把 PPFD 面板的 `CAL` 常數校成真實的 µmol·m⁻²·s⁻¹:在日光下用**同位置的
BH1750**去交叉校準 AS7341 光譜。搭配 `calibrate-ppfd.sh` 使用。原理見下一節
——之前這裡指向 `~/.claude/plans/` 底下的一份計畫,那個路徑不在版本控制內,
而且該檔名後來被另一份不相干的計畫覆蓋了,所以推導改為就地寫在這份文件裡。

## 開始之前 — 先確認光路是乾淨的(2026-08-14 新增)

**校準會把當下的光路狀態烘進 `CAL` 裡。** 感測器若正被遮擋或髒污,配出來的
係數就是「遮擋 + 感測器」的合成值,而且**驗收 gate 擋不住** —— ratio-drift 檢查
抓的是「隨亮度變化」的誤差,一個穩定的衰減會平平地通過。

所以動手前先看儀表板的 **`AS7341 clear ÷ BH1750 lux`**(告警規則
`spectrum-throughput-drift` 用的就是它,air.json panel 17 畫的是它的兩個分子分母):

| 值 | 意義 |
|---|---|
| 6.3 – 6.6 | 健康期實測基準 |
| 2.5 – 12 | 告警區間,落在裡面才可以校準 |
| 08-14 實測 **1.42** | AS7341 仍被遮擋約 4.5× —— **此時不可校準** |

比值回到區間內再做。這條規則會主動告訴你。

## 一句話原理

日光下,`lux/54` 是已知的 PPFD 參考(Apogee 的日光係數)。當兩顆感測器看到
**同一束日光**時,擬合 `CAL` 讓 AS7341 推出的
`PPFD = CAL·Σ(countᵢ/Rᵢ·λᵢ)` 等於 `lux/54`。精度約 ±15–20%(趨勢/DLI 等級,
不是實驗室等級)。

## 韌體設定(AS7341,`livingroom` 板)

- **ambient 讀取 Gain = 4×**(韌體 c9e0690 起,和 reflect 的 64× 分開;64× 會被
  日光爆表)、ATIME = 100、ASTEP = 999 → 積分時間 ≈ **280.78 ms**
- ADC 滿格(飽和)= **65535** counts;`mode=ambient` 的 payload **有**帶
  `saturated` 旗標(2026-08-14 查證:近兩天 10,883 筆)。工具沒有用這個旗標,
  它改以「任一通道 counts ≥ `--sat-count`(預設 65535)」推斷,結果等價。
- ⚠ **65535 有兩種來源,在資料裡長得一模一樣。** 一種是真的被光打滿;另一種是
  AS7341 卡在 I2C 上不回應時,driver 讀回來的 0xFFFF。後者從 2026-08-14 起
  反覆發生。**分辨方法是 `spectrum_read_ms`**:
  - 正常 **610 ms**(兩個 SMUX 週期 × 280.78 ms 積分)
  - 卡住時掉到 **44–336 ms** —— 積分根本沒跑完就回來了;也看過 7,894 ms 和
    17,255 ms 的逾時
  - 真飽和時 read_ms 維持正常,而且各通道會依自己的響應度依序爬到滿格;
    卡住時則會出現 f415 滿格而 f555 只有 16,157、下一筆完全倒過來,
    以及 1084、3203 這類跨通道重複的垃圾值
  2026-08-18 正午前後有 37 筆看起來完全像被太陽曬爆,實際不是 —— 當時
  lux 約 5,650,以健康比值 6.04 換算 clear 只會到約 34,000,離滿格還有距離。
  **修法是斷電**:用 Tapo app 把名為 `sensor` 的插座(192.168.50.52)關掉再開。
  它偶爾會自己好(最久觀察到 51 分鐘),但不可靠。
- 這組設定(gain 4×)的 datasheet 交叉檢查 CAL = **0.0037337**
- **面板現用值:`CAL = 0.0017469`**(2026-07-16 日光 fit,見「判讀結果」)。
  ⚠ **這個值已經失效** —— 它 fit 於 07-16,而 07-22 出現約 4× 的光學通量階躍
  (⚠ 幅度未定案:`VEGETATION-INDICES-PLAN.md` 記為 ~2.2×,兩處都沒寫推導 ——
  見 [`docs/incidents/2026-07.md`](../docs/incidents/2026-07.md#0722)),
  兩顆 BH1750 也已於 08-11 更換。必須重配,見「開始之前」。

## 感測器佈局(重要)

- `lux`(BH1750 @ 0x23)= 在植物位置,**被植物燈照到**。
- `lux_ref`(BH1750 @ 0x5C)= 約 10 cm 外,**遮掉植物燈** → 只有環境/日光。
  (`lux − lux_ref` ≈ 植物燈的貢獻。)
- **這個限制已經解除(2026-08 查證)**:AS7341 與兩顆 BH1750 現在都在
  **`livingroom`** 這塊板上(近兩天各約 11,000 筆),`staging-01` 只剩開發時
  偶爾上線。先前要求「參考 lux 必須跟 AS7341 同一塊板」的顧慮不再存在,直接
  用 `livingroom` 自己的 `lux` 即可。
- 驗證哪塊板上有哪些感測器,不要憑印象:

  ```bash
  docker exec monitor-air-influxdb influx query --org monitor-air '
  from(bucket:"sensors") |> range(start:-2d)
    |> filter(fn:(r)=> r._measurement=="spectrum" and r._field=="f555")
    |> group(columns:["device"]) |> count()'
  ```

## 什麼時候做

- **陰天可以 —— 甚至更好**(乾淨的漫射日光,天然低於爆表)。**不需要**晴天或
  開闊天空。
- **在中午前後做(約 10:00–15:00)。** 避開 **清晨/黃昏**(太陽角度低 = 光譜偏紅
  → `lux/54` 失準,而且變暗時比值會漂)和 **正午直曬**(兩顆都爆表)。
- 白天、以自然光為主(不是室內燈/人工光)。

## 你不需要開闊天空的位置

「不遮擋」指的是**兩顆感測器彼此要看到同一束光**,不是要有晴朗天空。
**開放陰影 / 白天有點遮蔽的陽台,就是合格的日光。** 把兩顆並排、朝同方向,
接受陽台當下有的日光即可。

## 擺法 — 兩種

**A. 關燈(工具目前就支援)。** 把 AS7341 放在主感測器 `lux` 旁邊;把植物燈
**關掉**,這樣 `lux` = 純日光。參考 = `lux`。

**B. 開燈、用 `lux_ref`(需要工具加一個小選項,尚未加)。** 把 AS7341 放在
**遮燈的** `lux_ref` 旁邊(兩者都只看環境日光、都看不到植物燈)。參考 = `lux_ref`。
好處是植物可以繼續補光。需要 `calibrate-ppfd.sh --lux-field lux_ref`(尚未加,工具會
拒絕這個參數)。**校準時請用擺法 A;擺法 B 是未來選項,現在別用。**

兩種都要:
- 兩顆**同平面、同傾角、彼此不互相遮擋**。
- **量測期間不要移動或改傾角**(幾何一漂,fit 就毀了)。

## 步驟

1. **確認 `livingroom` 同時在發光譜和 lux**(正常情況下本來就在發,這步只是確認)。
   用上面「感測器佈局」那段的查詢即可。2026-08-14 實測:近 30 天 `livingroom`
   有 157,601 筆光譜,`staging-01` 只有 707 筆 —— **不要用 staging-01**。
   (舊版這裡要求「讓 staging-01 上線」並宣告校準跑不動,那是 AS7341 還在測試板
   上時的狀況,硬體搬到 livingroom 之後就不成立了。)
2. 擺好感測器(擺法 A 或 B)、對應地關燈/開燈、選中午。
3. 收 **≥30–60 分鐘**。亮度有起伏(飄雲)最理想 —— 給比值漂移檢查有東西可查。
4. 記下開始時間。

## 跑校準

```bash
cd ~/monitor-air/broker
./calibrate-ppfd.sh --device livingroom --start -90m --gain 4 --tint-ms 280.78
# 偏暗/陰天就加:  --lux-min 500   ← 07-16 那次就用了(保留的 lux 低到 604,
#                                    而預設 --lux-min 是 3000)
# 只用單一 gain 的乾淨子窗(中途調過 gain 的話):--start/--stop 框那段
# 擺法 B: 需要 --lux-field lux_ref,尚未實作,傳了會被 unknown arg 擋掉
```

工具是**唯讀**的:只查 InfluxDB 並印出結果,不會改任何東西。`--device` 的預設
值是 `livingroom`,所以上面那個參數其實可以省略;寫出來是為了讓指令自我說明。

## 判讀結果

- **CAL(OLS)** ≈ **CAL(中位數)** —— 兩者差異小。
- **ratio-vs-lux 是平的** —— 真正的驗收關鍵(不能只看 R²)。漂移 > 30%
  → 幾何/光譜被污染 → 重擺、重收。
- **CAL_daylight 落在 CAL_datasheet(gain 4× → 0.0037)的 ~2× 內** —— 兩種獨立
  方法互相吻合 = 有信心。工具的合格帶是 0.5×–2×,出界會印 `DIVERGENT`。

  ⚠ **2026-07-16 那次是 0.47×,出界了,工具當時就印了 `DIVERGENT`。**
  本文件舊版把它解釋成「BH1750 比 Photone 低 ~1.4×,再乘 datasheet 法本身的
  ±2×」。**這個解釋現在不成立**:它依據的 Photone 讀數取自 2026-07-20,落在
  後來被判定為不穩定的低通量régime(同一顆感測器三天後高了約 4×),那批讀數
  已經整批撤回,不能支撐任何結論。我也沒有找到 1.4× 的獨立來源。

  所以誠實的狀態是:**這個 2× 落差目前沒有解釋,只是曾經被解釋過,而依據垮了。**
  重配時若再次出界,請當成待查項目,不要沿用舊說法把它說服過去。
- 然後(伺服器側):把 `CAL` 貼進 PPFD 面板(air.json id 9)。**目前貼的是
  0.0017469,已失效,等重配** —— 見「開始之前」。
- DLI 仍有兩張面板並存:id 7 是舊的 `lux/54`,id 11 是光譜積分。**先不要把
  光譜那張當成唯一真相** —— 它吃的就是這個待重配的 `CAL`。
  (舊版這裡寫「需 AS7341 先搬到植物位置」,那件事已經做完了。)

### 首次校準基準(2026-07-16 14:00–15:00,staging-01 陽台,gain 4×)
- CAL(OLS)=**0.0017469**、CAL(median)=0.0017958(差 2.7%)、R²=0.99、
  ratio drift 9%、lux 604–7121、60/60 分鐘保留。
- 驗收 gate(寫在 `calibrate-ppfd.sh` 裡,不是在這份文件裡):可用分鐘數 ≥ 20、
  lux 跨度 ≥ 2×、ratio-vs-lux 漂移 ≤ 30%。**R² 不是 gate** —— R² 高但比值隨亮度
  漂,是假的好結果。
- 教訓:整段窗前半在 64× 爆表 + 中途手調 gain → 必須限縮到 settle 後的**單一
  gain 乾淨子窗**才過驗收。光譜 telemetry 尚未帶 gain 欄位,無法事後回推 →
  見 `SENSOR-DRIFT-DESIGN.md`。

## 注意事項

- 精度只到 `lux/54` + 日光假設(~±15–20%),受 BH1750 精度限制。
- 裸板的角度/餘弦/視角不匹配可能是主要誤差 —— 靠「比值要平」把關;在兩顆上蓋
  一片白色漫射片有幫助(壓低到爆表以下 + 修正餘弦)。
- 對日光有效;在植物燈/室內光譜下的絕對精度只是近似(真要準就拿 PAR 計對一次)。
- 若韌體的 gain/積分時間變了,要重新校準。
